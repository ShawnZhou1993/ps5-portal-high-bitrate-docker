# 日常使用与排障

## 每次玩 PS5 的流程

**常驻模式（推荐，`up -d` 或 `docker run -d` 之后）：**

1. 确认 PS5 开机；
2. 直接在 Portal 上连接 PS5 —— 中继会自动捕获这次新握手并修改启动包；
3. 想观察效果：
   ```bash
   docker compose logs -f relay        # 或 docker logs -f portal-relay
   ```
   看到 `Startup modified, profile=65` 即本次握手已修改；
   在 Portal 的「设置 → 网络」或 Remote Play 连接信息里看目标码率是否提升。
4. 玩完直接断开即可，中继继续待命，不需要任何操作。

**临时模式（`docker compose run --rm relay try`）：**

1. Portal 先断开与 PS5 的连接；
2. 运行 `try`，等日志出现 `AUTO READY`；
3. 在 Portal 上连接 PS5，观察日志与画面；
4. Ctrl+C 停止，自动修复 Portal 的 ARP 表。

> 注意：必须是**新连接/新握手**才会被修改。如果连接发生在中继就绪之前，
> 日志会提示 `Stream detected without modified startup`，断开 Portal 重连即可。
>
> 如果断开重连多次仍然无效，把 Portal **长按电源键完全关机，等十几秒再开机**，
> 然后再连接——社区反馈 Portal 的 ARP 缓存很固执，完全重启往往才生效（上游 issue #2）。

**跑 baseline 时想看到实时进度？** 运行目录是绑定挂载到宿主机的，baseline 运行的
60 秒里，另开一个终端执行：

```bash
tail -F data/runtime/status.json        # compose 部署（注意是大写 F）
# docker run 部署（OpenWrt）：tail -F /opt/portal-relay/runtime/status.json
```

里面的 `forwarded_out` 会实时增长，它就是在数"收到并转发了多少个 Portal 的包"——
能看到数字上涨就说明链路是通的（上游 issue #2 有用户反馈 baseline 过程没有任何输出，
看了半天不知道发生了什么，这个方法可以实时确认）。

## 查看状态与日志

```bash
# compose 方式
docker compose ps
docker compose logs -f relay
docker compose run --rm relay status

# docker run 方式
docker ps
docker logs -f portal-relay
docker exec portal-relay portal status      # 容器内的上游助手
```

`status` 会输出 `status.json`（运行状态/转发计数/最后修改时间）、`recovery.json`
（上次恢复记录）等。关键字段：

| 字段 | 含义 |
| --- | --- |
| `forwarded_out` | Portal→PS5 方向转发包数；基线要求 > 0 |
| `unique_modified_startups` | 被修改的独立握手次数 |
| `state` | `running` / `stopped` / `recovery_failed` |
| `last_mutation` | 最后一次成功修改启动包的时间 |

## 切换码率档位

档位在注册时写入配置，切换需要重跑注册 + 基线：

```bash
# compose 方式
docker compose down
vi .env                       # 修改 PROFILE=65/100/200
docker compose run --rm relay configure-env    # 设备需开机
docker compose run --rm relay baseline         # Portal 断开后连接，保持 60s
docker compose up -d

# docker run 方式（OpenWrt）
docker stop -t 60 portal-relay && docker rm portal-relay
docker run ... -e PROFILE=100 portal-relay:local configure-env
docker run ... portal-relay:local baseline
docker run -d --name portal-relay ... portal-relay:local
```

建议先用 65 跑通全流程，再试 100；200 是实验性档位。
效果不理想时，断开 Portal 正常重连即可恢复原状（不改任何固件）。

## 故障对照表

| 现象 / 日志 | 原因与处理 |
| --- | --- |
| `NOT APPLIED: no matching new handshake` | 没捕获到新的 Portal 握手。断开 Portal，等中继就绪（AUTO READY）后再连；多次无效就把 Portal 完全关机重启 |
| 重连多次仍是 `NOT APPLIED` / 码率不提升 | Portal 没跟随 ARP 重定向。**长按电源键把 Portal 完全关机，等十几秒再开机**，然后连接（上游 issue #2 实证有效） |
| `UNCONFIRMED` | 包改了但没观察到连续高码率上报；重连或换 65 档，不要反复强制 |
| `forwarded_out` 保持 0，Portal 重定向后没数据 | 主机桥接流量被防火墙拦。见 OpenWrt 文档第 10 节（br_netfilter / iptables 放行） |
| `IPv4 forwarding is enabled` | 容器内转发未关。compose 检查 `sysctls` 段；docker run 检查 `--sysctl net.ipv4.ip_forward=0` |
| `no baseline for this config/code version` | 换了档位或升级代码后基线失效，重跑 `configure-env` + `baseline` |
| `address already in use` | 常驻服务还在运行。先 `down`（或停止旧容器）再跑 configure/baseline/try |
| `Previous relay recovery is unconfirmed` | 上次异常退出未确认恢复。运行 `repair` 后再启动 |
| Portal 连不上 PS5（几分钟内） | 容器被强制杀死（`rm -f` / 掉电）。把 Portal 断开重连刷新 ARP；或运行 `repair` |
| Portal 画面卡顿/模糊 | 对比 65 和 100 档；200 不一定更好。断开重连恢复默认 |
| 注册时报 `wake the device and verify its IP` | 设备关机/休眠或 IP 不对。确认 PS5、Portal 开机且 IP 正确（建议 DHCP 保留） |
| 路由器上跑中继后其他设备上网异常 | 不应发生（只针对这一对设备做 ARP 应答）。若出现，立即停止容器排查父接口是否选错 |
| 构建时报 `set: line 10: illegal option -` | 构建上下文带 CRLF 行尾（常见于从 Windows 签出/复制的文件）。`ash` 把 `\r` 当非法选项。修复：`find <包目录>/src -type f -exec sh -c 'tr -d "\015" < "$1" > "$1.tmp" && mv "$1.tmp" "$1"' _ {} \;` 后重新构建（本部署包 zip 内已全部为 LF，Dockerfile 也有自动去 CR 防御） |

## 修复命令（unclean stop 之后）

```bash
# compose
docker compose run --rm relay repair

# docker run（容器已停止时）
docker run --rm -it \
  --network portal-lan --ip 192.168.1.215 \
  --sysctl net.ipv4.ip_forward=0 --cap-add NET_RAW --init --tmpfs /run \
  -v /opt/portal-relay/config:/etc/portal-bitrate \
  -v /opt/portal-relay/runtime:/var/lib/portal-bitrate-auto \
  portal-relay:local repair
```

## 停止中继

```bash
docker compose down              # 优雅停止，自动修复 Portal ARP（约几秒）
# 或
docker stop -t 60 portal-relay && docker rm portal-relay
```

停止后 Portal 与 PS5 恢复直连，码率设置随下次握手自然恢复，无残留。

## 社区反馈参考（上游 issue #2）

上游 [issue #2](https://github.com/atameric/ps5-portal-high-bitrate/issues/2)
（OpenWrt 系路由器 iStoreOS 上原生部署的用户）反馈了四个点，对照本部署包：

| 用户反馈 | 本部署包的情况 |
| --- | --- |
| ① `ip_forward=0` 检查在路由器上过不去（NAT 路由器必须开转发） | **无需打补丁**：容器有独立的网络命名空间，`--sysctl net.ipv4.ip_forward=0` 只作用于容器内部，路由器的转发和上网不受任何影响。这正是用 macvlan 容器而不是原生安装的原因之一 |
| ② scapy 的 L2socket 在桥接接口（br-lan）上收不到包（tcpdump 却能收到） | 本包的 socket 绑定的是容器内 macvlan 的 `eth0`，**不是 br-lan**，不经过这条代码路径；若确实遇到"tcpdump 看得到、relay 计数不动"，按 OpenWrt 文档排障第 4 条处理 |
| ③ ARP 欺骗需要 Portal **完全关机重启**才生效 | 已写入各部署文档：Remote Play 里断开重连无效时，长按电源完全关机、等十几秒再开机 |
| ④ baseline 运行过程没有任何输出，看不懂在做什么 | 运行目录绑定挂载在宿主机上，可实时查看 `data/runtime/status.json` 的 `forwarded_out` 计数（见上文"跑 baseline 时想看到实时进度"） |

该用户最终效果：65 档下 Portal 显示的目标码率约 20 → 40 Mbps。
注意 PS5 上报的目标码率通常高于 Portal 实际显示值，以 Portal 界面为准。

## 安全与隐私

- 仅对**你自有**的 PS5/Portal 生效，请勿在公共网络部署；
- `data/config/auto-config.json`、`data/runtime/` 里有设备信息和运行数据，勿外传；
- 容器不映射任何端口，无需开放防火墙端口；
- 该工具不修改任何固件，不涉及越狱；随时可彻底停用。
